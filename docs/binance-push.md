# Binance notifications on iPhone

The existing VAPID keys, private pairing token and eight device slots are reused. No keys are generated or rotated. Existing devices without topic metadata remain MT4-only until the owner explicitly updates their preferences on `/push.html`. Registering or updating a device still requires `PUSH_PAIRING_TOKEN` and the configured same-origin header; the relay token cannot pair devices. No Binance API key is used by this feature. Pairing codes are never put in URLs or stored by the client.

Open `/push.html` in Safari, add to Home Screen, launch from its icon, enter the pairing code, choose topics, enable notifications and send a test. Supported on iOS/iPadOS 16.4+. The owner must grant OS permission on the target device. Delivery depends on internet, notification permissions, Focus and push services; an accepted request is not proof of receipt.

`binance-push-monitor` is a Netlify scheduled function running once per minute on the published production deploy, even with the browser closed. It reads only GET `/api/binance-action-log` and, when signal alerts are selected, GET `/api/binance-agent`. No trading endpoint or server process is changed. Pairing time and per-topic opt-in timestamps exclude prior trades. Only LIVE FILLED BUY/SELL actions produce execution messages. The optional Wyckoff signal channel is clearly labeled as analysis, not a fill; it requires a fresh confirmed pattern on a non-held asset and deduplicates by pattern identity. Signals arising and disappearing between one-minute polls can be missed. Logs/events older than ten minutes are not replayed, including after a prolonged outage. No delivery guarantees are made.

Trade messages contain symbol, execution price, quote amount when available, local Israel time, and sell net P&L only when the net journal explicitly contains it (unknown commissions stay unknown). Source action logs and account balances are not persisted in the notification store. Per-device hashed event claims prevent overlapping polls from sending the same accepted event repeatedly. Transient push errors are retried on later polls within the event window; expired 404/410 subscriptions are removed. Crash leases expire after two minutes. A crash after provider acceptance but before saving that acceptance can cause a retry, with the same notification tag/topic. Delivery is bounded to keep the scheduled function within its runtime budget; the provider timeout is six seconds. Only opted-in MT4 devices receive legacy relay notifications.

`push-api?action=config` exposes the public VAPID key and generic poll timestamp/health, never private keys, tokens or device endpoints. Authenticated `status` reports only the requesting subscription's registration and aggregate monitor health. Tapping a trade notification opens `/binance-agent.html`; navigation is restricted to known local destinations. No user SMS service or local desktop agent is needed. Netlify usage/quotas still apply.

Private-feed authentication: configure the same dedicated `BINANCE_PUSH_READ_TOKEN` in the VM service environment and Netlify production Functions environment before the coordinated stability release. Use a random 32-byte hex value, distinct from the trading control token. This credential permits only GET `/api/binance-action-log` and GET `/api/binance-agent`; it cannot read the account endpoint or issue controls. The function sends it only to the fixed backend origin and refuses redirects. Missing or invalid credentials stop the poll without sending or advancing event claims. Never expose this value in browser assets, build output, logs or source control.

Validation: causal event filters, old-event exclusion, legacy isolation, safe P&L formatting, pattern identity, authenticated pairing/status, per-device retry, concurrent delivery claims, expired subscription removal, authenticated GET-only polling, missing-token failure, denial of account/control access, safe click destinations, existing encrypted-push dependency tests, and client DOM activation tests. Actual iPhone lock-screen receipt requires the owner's on-device opt-in and test.
